**Phase 1**

2. Quote: “`lsp_port`: Attach to an already running editor on this port instead of spawning.” / LSP startup step 1: “Resolve ... Godot binary.” / step 2 skips only steps 3 to 7.

Problem: Attach mode either unnecessarily requires a locally discoverable Godot binary or bypasses the explicitly ordered resolution step.

Exact fix text: “Validate settings and resolve the project first. When `lsp_port` is set, do not resolve or validate a Godot binary; connect directly to the configured editor. Resolve the Godot binary only before a managed spawn.”

**Phase 2**

3. Quote: “`dap_config_to_scenario`: ... A program ending `.tscn` becomes ...; anything else ...; request `launch`.”

Problem: `zed_extension_api 0.7` supplies `DebugConfig.request` as `DebugRequest::Launch(LaunchRequest)` or `DebugRequest::Attach(AttachRequest)`. Attach has no program, so implementations must guess whether to reject it, convert it to launch, or produce an attach scenario.

Exact fix text: “For `DebugRequest::Launch`, derive `scene` from `LaunchRequest.program` and return request `launch`. For `DebugRequest::Attach`, return a configuration containing `{ "request": "attach" }`; ignore `process_id`, because Godot attaches through its project DAP endpoint.”

**Phase 3**

4. Quote: “`open_docs: uri -> ...`” / “URIs are percent-encoded canonical `file://` URIs, built with one function used everywhere.”

Problem: The spec does not explicitly apply canonicalization to URIs received from Zed. Raw and watcher-generated spellings of the same file can become separate entries, allowing synthetic disk content to overwrite ownership of an unsaved Zed document.

Exact fix text: “Use the canonical absolute filesystem path as document identity. Normalize every local file URI received from Zed and every watcher path through the shared URI function before `open_docs` lookup, storage, or forwarding. Preserve enough identity after deletion for `didClose` to find the existing entry.”

**Phase 4**

5. Quote: “If a valid detached `gui` state exists ... print it ... Otherwise remove stale state ... launch [another GUI].” / During handoff, GUI state is recorded before both ports become ready.

Problem: A GUI with matching live PID but temporarily unavailable ports is classified as stale. A replacement bridge can then launch a second editor. Failure cleanup for newly spawned detached GUIs is also undefined.

Exact fix text: “A matching live GUI PID is never removed or replaced solely because its ports are not yet accepting connections. Wait for both ports using the startup deadline; if they remain unavailable, return an error without launching another editor. Record standalone GUI state as `starting` immediately after spawn. On failure of a newly spawned GUI, terminate and reap its process group before removing state or starting headless recovery.”
